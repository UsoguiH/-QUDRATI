# قدراتي — QUDRATI

**This is a real, published project. It is live at [qudrati.xyz](https://qudrati.xyz/) and available on Android as `Qudrati.apk`. Treat all changes as production code.**

## What it is

A Duolingo-style Arabic web game for practicing the Quantitative section of the Saudi General Aptitude Test (GAT / Qiyas). Fully RTL, Arabic-first, zero dependencies, zero server, zero build toolchain. Open `index.html` and play.

## Tech stack

- **Pure HTML/CSS/JS** — no npm, no bundler, no framework
- **State**: single `S` object in `localStorage["qudratState"]`
- **CSS**: pixel-perfect implementation of the Duolingo design system (colors/radii extracted from Figma file `sCGqaL307LkNrY35xnV66O`)
- **Font**: Baloo Bhaijaan 2 (Arabic rounded equivalent of Duolingo's DIN 2014 Rounded VF)
- **Android**: Capacitor wrapper → `Qudrati.apk`

## Question schema

```js
{
  id: "unique-id",           // e.g. "oo-01" — must be globally unique
  format: "mcq",             // or "comparison"
  difficulty: 2,             // 1=easy, 2=medium, 3=hard
  track: "both",             // "both" | "sci" | "lit"
  stem: "نص السؤال…",
  choices: ["أ","ب","جـ","د"], // mcq only — 4 items, no letter prefix
  // value1: "…", value2: "…", // comparison only
  answer: 0,                 // 0-indexed correct choice
  solution: "الحل خطوة…",   // step-by-step, \n between steps (≥10 chars)
  method: "١) …\n٢) …\n💡 …", // structured method steps (optional but preferred)
  figure: null               // or inline SVG / HTML table string
}
```

Lessons also carry `stars`, `xp`, `pages`, `category`, `goal`, `rules[{n,name,formula,when}]`, `notes`,
`tricks`, an optional `figure`, and a flat `method` string (the fallback the method sheet shows).

Comparison answers must use the fixed 4-choice set defined in `CMP_CHOICES` (app.js line ~12):
`["القيمة الأولى أكبر", "القيمة الثانية أكبر", "القيمتان متساويتان", "المعطيات غير كافية"]`

## Validating the question bank

```bash
node tools/validate.js
```

Checks: unique IDs, valid format/difficulty/track/answer, solution length, figure tag, duplicate choices, comparison answer distribution.
The difficulty ramp is checked by `node tools/validate_teach.js` instead, which knows the chunks: a
student meets a chunk's questions sorted by difficulty, so that validator lists every step wider than
one star as a cliff still to bridge.

**The four data files are generated — never hand-edit them.** To change content, edit
`qudrat-lessons-duolingo.md` and run:

```bash
python tools/import_curriculum.py          # --check parses and reconciles without writing
node tools/validate.js
```

The importer refuses any line it cannot parse and reconciles every count against the
file's own map; a question that says «في الشكل» must have an SVG in `tools/curriculum_figures.py`.

**The public pages are built from the same data.** After any change to `js/data/*.js`, `teach.js`,
`teach-figures.js`, `learn.js`, about.html's JSON-LD or content.css's font, run

```bash
node tools/build_lesson_pages.js && node tools/build_sitemap.js
```

and commit their output with the change (both have `--check`; the SEO audit runs them too).

## Adding features

- **Sound: Brilliant's effects for everything, our correct answer and Duolingo's files kept** (`snd`, `SND_MAP`, `SND_FILES`; the user, 2026-10-27). A moment that makes a sound calls `snd("moment-id", oldSound, file?)`: the id's Brilliant file from `SND_MAP` (the picks in tools/brilliant-sounds/moments.json) plays from assets/sounds/bri/, a call site may pass its own file (a choice's pitch by its slot, toggle on / off) or `""` for silence, and a moment with no Brilliant sound or a file not yet decoded plays `oldSound`. `playCorrect` and every Duolingo file (`sfxPlay` with a Duolingo key) never pass through it. The user's own three: the in-lesson streak sting on **every** answer that lights the bar (run ≥ 3, `answer-run`), the chest's three hits as one short click a step higher each (`assessment-click-option-1` at rates 1 / 1.12 / 1.26; the user, 2026-10-28: «make the three click sounds better and simpler» — the tallies before rang 1.6s and ran into each other), then level-mastered as it opens, stopped at 2.4s before its last hit (`SND_END`), and the gem pile and its count silent (`chest-gems-reveal` / `-tick` map to `""`; the user, 2026-10-28: «the last part in voice at opening the chest»), and each matched pair a tally higher than the last, the last pair too, and then the correct sound (the user, 2026-10-28: «now I hear 3 voices and 4 is Duolingo … we want 4 voices and then» it). Loading comes in three bites for mobile data: `SND_FIRST` on the first touch, all of it the moment a lesson opens (`A.startLearn` / `A.startLesson`, again in `warmStreak`; warming only after the first answer let a «وصّل» before it play the old beeps — the user, 2026-10-28: «it's the old sound») or the first time one is missing, `SND_CHEST` when the chest opens. A new sound moment gets an id and a Brilliant pick, never a new synth beep.

- **A fraction is drawn as the exam prints it** — the top number over a bar over the bottom one, never «١/٢» on the line (`fracs()` beside `esc` in app.js, `.fr` / `.fr-n` / `.fr-d` in style.css; the user, 2026-10-28: «this is not like qudrati كسور … make it like qudrati exam كسور»). Data keeps writing «١/٢»; the renderers turn it: `learnFmt` (every short-lesson text), `questionBody` (stem, values, choices), `formatExplain` (solutions), the answer lines, the review lists, the teaching cards and their checks, the guidebook. Text inside an `<svg>` is left alone, so a figure says it in words; counts such as «٢/٨ دروس» and scores are not fractions and never go through it. A new place that shows question or lesson text passes it through `fracs` (after `esc`).

- **No step scrolls** (the user, 2026-10-29: «no scrolling at all, I don't want any screen to have me able to scroll it»; they saw the taste screen and «وش هو قدراتي؟» scroll on their phone, about 387×687 in Chrome). Every screen without the tab bar — the first run, a question, a teaching card, a win, a result, signing in — fits the phone, and so do the rule books: a book taller than its sheet comes in pages swiped sideways (`bookPages`: cut by measuring, a lesson's heading never left alone at a page's foot, each of the unit book's lessons on its own page, a dot a page or «٣ من ٤٥» on a long book, the unit book opening on its contents (`.bk-ix`, a tap goes to the lesson's page, «٣ من ٤٥» goes back), cut again on a turn or a late font; the book's sheet sits above the tab bar, which used to cover «رجوع»). The tab pages (path, league, stats, settings, the mock and review homes) are lists and still scroll. `fitNow` (foot of app.js) runs before a screen's first paint and again on any change (a `MutationObserver` on `#app`, a `ResizeObserver` a frame later, a resize, a late font) — at most once a frame (`fitSoon`), and only for a change inside what it fits (`fitTouched`): measuring lays the page out twice, and the mock's clock paid that every second. It zooms the screen's body down to the largest size that fits, never under `FIT_MIN`: a question's `.q-area` children, else `.ob-stage` / `.wl-body` / `.teach-body` / `.complete` / `.exam-pick`. A change while the screen is up glides (`id: "fit"`), and a body zoomed earlier is searched again from full size whenever something changed size (`why` "size": a resize, a late font, content that grew or shrank; a bare DOM change only ever shrinks it), so it grows back once what was tall has gone (an overflow never reads below zero, so it used to stay small: the mock sat at 83% on a phone where it fits). A screen may opt out with `data-fit="off"`, or ask to be fitted without a glide with `data-fit="still"`. Nothing on a first-run screen may widen the page either (`.ob-screen { overflow-x: clip }`): «جرّب»'s rule card pops in at 112%, ran 10px past both edges, and the phone scrolled sideways after it and back — a shake the user saw (2026-10-30). The welcome screen is `off` while the loading screen's copies fly and `still` once they land, since `qsHold` glides its column itself (a zoom glide on top fought it: 3.8px back and forth on a turn mid-flight). It measures the screen at rest (`fitSettled`: finite animations seeked to their end and script-set transforms lifted, all put back in the same task; running transitions are left alone). - **Endless animations run on the GPU** (the 2026-10-30 performance pass: 100k students, many on slow phones). An infinite loop animates `transform` or `opacity`, never `background-position` (the finished node's shine moves a band by transform inside a clipped box, `.nd-shine`, with `overflow: hidden`, since `clip-path` alone still lets the page scroll to what it hides); an entrance that runs before a loop on the same element animates `scale` / `translate`, not `transform` (`springInS`, `obDuoInS`, `lbbTailLS`, `chestTipInS`: a finished entrance on `transform` keeps the loop off the GPU); nothing that loops sits under a `zoom`; a Rive file is cleaned up whenever its screen is left (`go` stops the win screens'). - **Word and number chips answer with Duolingo's own wave** (`adWave`, `AD_JUMP`, `AD_SQ`, `AD_SLAB`; from the decompiled app's Compose TapInput `AtomicDelightAnimation`; the user, 2026-10-26: «any question similar to this … they jump after each other … green also»). - **Every answer jumps — and only answers.** Whenever a student picks or submits an answer to a question — a lesson, a short lesson, a teaching check, the taste question, the level test, the mock exam — the answer card plays the lessons' correct-answer jump (`fxAddJump`, via `obJump` / `teachFx` / the lesson's own fx). The one exception is the first run's «جرّب» tap, which only selects; its right answer jumps when the answer is shown (the user, 2026-10-26).

- All rendering is done by functions in `js/app.js` that return HTML strings and set `$app.innerHTML`.

## Deployment

Static hosting, no server required. The app is live at **qudrati.xyz**. The Android APK (`Qudrati.apk`) is a Capacitor wrapper over the same static files.

**Bump `VERSION` in `sw.js` whenever a shell file changes** — the page, the CSS, the app, the four data files, the teaching data or a glyph — and keep the two `?v=` numbers in `index.html` identical to it. A student with an active worker reads the shell from a cache named after that version, so new content reaches them when the name changes and not before. The worker never caches a dev harness or anything a harness loads, so `preview.html` and `mobile.html` keep showing the file on disk. The content pages (qudrat/, about, privacy, the guide, the mock page, qudrat-methods.html, content.css, the font, qudrat/img/) are not shell files: the worker fetches them network-first and only falls back to its copy offline, so changing them needs no bump. **index.html, js/app.js, css/style.css and sw.js ship together**: the working index.html's loading screen waits for `splashOut` in app.js and only gives up after 20s, so a new index.html over an old app.js shows the loading screen that long (`node tools/build_sitemap.js --seo-only-index OUT` writes HEAD's index.html with only the SEO head and pre-render changed, at HEAD's `?v=`, for a deploy that leaves the app alone).
